# xray-auto-install

Один скрипт — один результат: рабочая `vless://` ссылка. Никакого Docker, никакой
панели управления — чистый systemd-сервис Xray-core на голом Debian/Ubuntu.

Спрашивает только IP сервера и root-пароль, выданный провайдером. Всё остальное —
автоматически, повторяя ровно ту схему, что была вручную проверена (включая полную
перезагрузку сервера) на тестовом сервере 2026-09-09.

## Что делает

1. Обновляет пакеты, ставит `curl unzip nginx openssl nftables`.
2. Включает BBR (персистентно, переживает перезагрузку).
3. Ставит официальным установщиком `XTLS/Xray-install` **последний стабильный**
   релиз Xray-core (установщик сам резолвит `/releases/latest`, что уже
   исключает pre-release теги).
4. Генерирует UUID, X25519-пару (Reality) и постквантовую VLESS-пару шифрования
   (`mlkem768x25519plus`) через `xray vlessenc`.
5. Поднимает локальную заглушку под Reality `dest` — nginx на `127.0.0.1:8444`
   с самоподписанным сертификатом (`CN=www.microsoft.com`). Заглушка не торчит
   наружу, доп. проброса портов не требует.
6. Пишет `/usr/local/etc/xray/config.json`: VLESS + XHTTP (транспорт) + Reality
   (маскировка) + `xtls-rprx-vision` (flow) + PQC-шифрование. Именно эта
   комбинация требует PQC — `encryption: none` с `xhttp`+`vision` не работает
   (`XTLS only supports TLS and REALITY directly for now`).
7. Генерирует новый SSH-ключ, добавляет его на сервер и **проверяет новым
   соединением**, прежде чем что-либо трогать в sshd.
8. Отключает парольный вход (`PasswordAuthentication no`), добавляет
   `X11Forwarding no`, `MaxAuthTries 3`, `LoginGraceTime 30` — с проверкой новым
   соединением на каждом шаге.
9. Включает nftables (policy drop, открыты только 22/tcp и 443/tcp) — со
   встроенным failsafe: если правила окажутся кривыми, через 2 минуты фоновый
   таймер на сервере сам их сбросит (`nft flush ruleset`).
10. Выводит готовую ссылку и сохраняет сводку в
    `~/xray-auto-install-<ip>-summary.txt`.

## Использование

```bash
./install.sh
```

Спросит:
- `Server IP`
- `Root password` (от провайдера)

На выходе — ссылка вида:

```
vless://<uuid>@<ip>:443?encryption=mlkem768x25519plus...&flow=xtls-rprx-vision&security=reality&sni=www.microsoft.com&fp=firefox&pbk=...&sid=...&spx=%2F&type=xhttp#xray-auto-install
```

Нужен клиент с поддержкой VLESS Encryption (PQC) — свежие v2rayNG / Happ /
sing-box. `fp=firefox` выбран по умолчанию: на тесте `fp=chrome` не заработал
на реальном мобильном клиенте, `fp=firefox` — заработал (причина
клиент-специфична, не выяснялась).

## Требования к локальной машине

`ssh`, `sshpass`, `ssh-keygen`. Целевой сервер — чистый Debian/Ubuntu с root-
доступом по паролю (как выдаёт провайдер).

## Что сознательно НЕ делается

Решение основано на предметном обсуждении угроз для этого класса серверов
(одноразовый/малый VPN-сервер, а не мультиарендная инфраструктура):

- **Отдельный sudo-пользователь** — не добавляет защиты при полной
  компрометации машины: тот, кто получил доступ (украл ключ, взломал сервис),
  и так может стать root.
- **fail2ban** — на сервере нет парольной аутентификации ни для SSH (ключ
  only), ни для какого-либо другого сервиса — банить нечего.
- **Passphrase на SSH-ключе** — защищает только от кражи ключа "в холодную"
  (файл утащили, но не получили доступ к разблокированной машине). Реалистичная
  модель угроз здесь — полная компрометация локальной машины целиком, при
  которой passphrase не спасает.
- **swap** — не относится к безопасности, отдельный осознанный выбор не
  усложнять первичную установку.

Если твоя модель угроз другая (много клиентов на сервере, общий доступ к
локальной машине, требования комплаенса) — добавляй это поверх сознательно,
скрипт не мешает.

## Файлы на сервере после установки

- `/usr/local/etc/xray/config.json` — конфиг Xray-core
- `/etc/nginx/conf.d/fakesite.conf` + `/etc/nginx/fakesite-ssl/` — заглушка dest
- `/etc/nftables.conf` — правила фаервола
- `/etc/ssh/sshd_config.d/00-hardening.conf`, `00-disable-password.conf`
- `/etc/sysctl.d/99-bbr.conf`, `/etc/modules-load.d/bbr.conf` — BBR
