# xray-auto-install

Один скрипт — один результат: рабочая `vless://` ссылка. Никакого Docker, никакой
панели управления — чистый systemd-сервис Xray-core на голом Debian/Ubuntu.

Спрашивает только IP сервера и root-пароль, выданный провайдером. Всё остальное —
автоматически: система, Xray-core, ключи, Reality, SSH-hardening, firewall. Каждый
этап проверен на живом VPS, включая полную перезагрузку сервера, а для проверки
готового сервера есть отдельный `verify.sh`.

## Быстрый старт

Скрипт запускается **на своей машине** (Linux/macOS с `bash`, `ssh`, `sshpass`), а
не на сервере — он сам подключается к серверу по SSH:

```bash
bash <(wget -qO- https://raw.githubusercontent.com/RamDll/xray-auto-install/main/install.sh)
```

Спросит IP и root-пароль, дальше без участия. Скрипт интерактивный (`read`) —
именно поэтому `bash <(...)` (process substitution), а не `... | bash`: во втором
случае stdin занят телом скрипта и `read` не сможет прочитать твой ввод с терминала.

Для `verify.sh` (см. ниже) нужен клон репозитория — удобнее сразу так:

```bash
git clone https://github.com/RamDll/xray-auto-install.git && cd xray-auto-install
./install.sh
./verify.sh <IP>
```

## Что делает

1. Готовит систему: сразу отказывается на Debian < 12 / Ubuntu < 22.04; снимает
   apt-daily/unattended-upgrades (чтобы не держали dpkg-lock на свежем VPS),
   чинит незавершённый `dpkg` и сломанные зависимости прошлых прогонов
   (`dpkg --configure -a`, `apt-get -f install`), делает `apt dist-upgrade`
   (свежий образ провайдера может нести старые версии с известными дырами),
   ставит нужные пакеты (`curl unzip openssl nftables`) с ретраями, проверяет
   синхронизацию времени (важно для TLS/Reality) — все apt-вызовы идут с
   ожиданием dpkg-lock и тремя попытками.
2. Включает BBR (персистентно, переживает перезагрузку).
3. Выбирает Reality SNI/target — см. [Reality: выбор SNI](#reality-выбор-sni).
4. Ставит официальным установщиком `XTLS/Xray-install` **последний стабильный**
   релиз Xray-core: установщик скачивается в файл через `curl --fail` и только
   потом запускается — оба кода возврата проверяются, всё с ретраями.
   Установленная версия печатается в конце установки и пишется в summary.
5. Генерирует UUID, X25519-пару (Reality) и VLESS-пару шифрования
   (`mlkem768x25519plus`) через `xray vlessenc` — см.
   [VLESS Encryption](#vless-encryption-что-именно-постквантовое). Сырой вывод
   генераторов ключей не печатается никогда, даже при ошибке.
6. Пишет `/usr/local/etc/xray/config.json` (права `640 root:<группа xray>`):
   VLESS + XHTTP (транспорт) + Reality (маскировка) + `xtls-rprx-vision` (flow) +
   VLESS Encryption. Какая-то форма VLESS Encryption тут обязательна —
   `encryption: none` с `xhttp`+`vision` не работает (`XTLS only supports TLS and
   REALITY directly for now`). Перед запуском конфиг проверяется
   `xray run -test`. Домой уходят только значения для ссылки: приватный ключ
   Reality и `decryption` остаются на сервере.
7. Генерирует новый SSH-ключ, добавляет его на сервер и **проверяет новым
   соединением**, прежде чем что-либо трогать в sshd. Хост-ключ сервера
   закрепляется в отдельном `~/.ssh/xray-auto-install-<ip>.known_hosts`
   (основной `~/.ssh/known_hosts` не трогается).
8. SSH-hardening в два шага, всё — одним нашим файлом
   `/etc/ssh/sshd_config.d/00-xray-auto-install.conf`; чужие конфиги
   (`sshd_config`, `50-cloud-init.conf`) не трогаются, поэтому откат — это
   удалить наш файл и сделать reload:
   - сначала безобидная часть (`X11Forwarding no`, `MaxAuthTries 3`,
     `LoginGraceTime 30`) с проверкой новым соединением, пока пароль ещё жив;
   - потом отключение пароля (`PasswordAuthentication no`,
     `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`).
   Перед записью скрипт проверяет, что в `sshd_config` активный
   `Include /etc/ssh/sshd_config.d/*.conf` стоит выше любой из этих директив
   (sshd берёт первое вхождение — директива выше Include перебила бы наш
   файл); если нет — отказ с объяснением, а не правка чужого файла. Дальше —
   `sshd -t`, reload (с поддержкой socket-activated SSH на Debian trixie),
   локальная самопроверка порта и строгая проверка `sshd -T -C` для реального
   адреса клиента (с учётом `Match`): любое отклонение от ожидаемых значений —
   откат и остановка. Страховочный `systemd-run`-таймер на 3 минуты ставится
   **до** отключения пароля и проверяется; без него пароль не отключается.
   Снимается только после того, как скрипт подтвердит новое соединение по
   ключу.
9. Включает nftables (policy drop, открыты только 22/tcp и 443/tcp): синтаксис
   проверяется (`nft -c -f`) до применения, плюс страховочный
   `systemd-run`-таймер на 2 минуты, поставленный до применения. **Откат
   аварийный:** он не восстанавливает прежний firewall, а снимает фильтрацию
   целиком (`nft flush ruleset`, `disable nftables`, пустой
   `/etc/nftables.conf`) — так, чтобы она не вернулась и после перезагрузки.
   Если доступ после firewall не подтверждён — скрипт останавливается и
   ссылку не выдаёт. Следом поднимает `nf_conntrack_max` до 32768 (дефолт
   ~8192 на VPS с ~1ГБ RAM хватает на 1-2 человек — современная веб-страница у
   одного клиента легко держит десятки параллельных соединений, при нескольких
   активных пользователях таблица переполняется и новые соединения молча
   дропаются; цена — доли МБ RAM).
10. Выводит готовую ссылку, версию Xray-core и сохраняет сводку в
    `~/xray-auto-install-<ip>-summary.txt` (права 600 — в ней ссылка с ключами).

Устойчивость к сбоям на свежем VPS (dpkg-lock, socket-activated SSH, автооткат
по таймеру) унаследована из [ovpn-stack](https://github.com/RamDll/ovpn-stack)
`install/bootstrap.sh` — там эти проблемы всплывали на реальных прогонах и были
исправлены раньше.

## Reality: выбор SNI

**Зачем пул.** Reality маскирует сервер под настоящий сайт: `target` — реальный
`<домен>:443`, и любой неавторизованный клиент (сканер, браузер, зонд цензора)
получает подлинный сертификат и ответ этого сайта, а не заглушку. Если бы все
установки этого скрипта использовали один и тот же домен, это был бы лишний
признак для массового сканирования — поэтому домен выбирается случайно из пула:

`www.microsoft.com`, `www.bing.com`, `www.samsung.com`, `www.nvidia.com`,
`www.amd.com`, `www.intel.com`, `www.tesla.com`, `www.sap.com`, `www.oracle.com`,
`www.dell.com`, `www.cisco.com`, `www.qualcomm.com`, `www.hp.com`.

**Чего в пуле нет и почему:**
- **apple / icloud** — Xray-core сам предупреждает в логе: `Choosing apple,
  icloud, etc. as the target may get your IP blocked by the GFW`.
- **CDN-фронты** (cloudflare, jsdelivr) — их сертификат и поведение слишком
  сильно зависят от точки входа.
- **www.lenovo.com** — с сервера проходил все проверки, но трафик клиента по
  нему резал провайдер (с `www.hp.com` на том же сервере и тех же ключах —
  работало).

**Как проверяется.** На сервере, после синхронизации времени, пул
перемешивается, и берётся первый домен, к которому **с этого VPS** проходит
`openssl s_client -tls1_3 -groups X25519 -alpn h2 -verify_return_error
-verify_hostname <домен>` — TLS 1.3, X25519, валидный для домена сертификат, **и**
в выводе реально есть `ALPN protocol: h2` (код возврата s_client согласование h2
не подтверждает). Не прошёл ни один — установка останавливается с подсказкой
(DNS / время / исходящий 443).

**Ручной выбор.** Серверная проверка не видит, как к домену относится
провайдер **клиента** (см. lenovo выше). Если домен уже проверен у своего
провайдера — задай его явно:

```bash
XAI_REALITY_SNI=www.hp.com ./install.sh
```

Заданный домен проверяется с сервера той же командой; не прошёл — установка
останавливается, а не подставляет случайный.

**Оставшееся ограничение — несоответствие ASN.** IP сервера принадлежит
хостинг-провайдеру, а сертификат — Microsoft/HP/…; наблюдатель, сверяющий SNI с
владельцем IP, это различие видит. Закрывается только self-steal (свой домен на
этом же сервере) или target из той же сети — оба сознательно не сделаны, см.
[Что сознательно НЕ делается](#что-сознательно-не-делается).

## VLESS Encryption: что именно постквантовое

`xray vlessenc` печатает два варианта. **В обоих обмен ключами один и тот же —
гибридный ML-KEM-768 + X25519, эфемерный**: трафик, записанный сегодня, не
расшифровать и будущим квантовым компьютером (защита от
harvest-now-decrypt-later). Различается только **аутентификация сервера**:

| Вариант | Аутентификация сервера | Размер значений |
|---|---|---|
| `X25519, not Post-Quantum` — **выбран** | X25519: не защищена от будущего *активного* квантового MITM | ~44 символа |
| `ML-KEM-768, Post-Quantum` | ML-KEM-768 | ~1600+ символов |

Выбран короткий: подмена сервера в реальном времени квантовым компьютером —
угроза другого порядка, чем пассивная запись трафика, а длинный вариант
превращает ссылку/QR в кирпич текста.

Внешний TLS у Reality — классический; постквантовость даёт именно внутренний
слой VLESS Encryption.

## Использование

```bash
./install.sh
```

Спросит:
- `Server IP` — только IPv4 (4 числа 0–255, без ведущих нулей; IPv6 и имена
  хостов не принимаются);
- `Root password` (от провайдера).

На выходе — ссылка вида:

```
vless://<uuid>@<ip>:443?encryption=mlkem768x25519plus.native.0rtt...&flow=xtls-rprx-vision&security=reality&sni=<домен>&fp=firefox&pbk=...&sid=...&spx=%2F&type=xhttp#<ip>
```

Нужен клиент с поддержкой VLESS Encryption — свежие v2rayNG / Happ /
sing-box. `fp=firefox` выбран по умолчанию: на тесте `fp=chrome` не заработал
на реальном мобильном клиенте, `fp=firefox` — заработал (причина
клиент-специфична, не выяснялась). В отличие от SNI, `fp` **не рандомизируется**:
случайные `ios`/`android`/`qq` дают неправдоподобные комбинации с реальным
клиентом (см. `ovpn-stack` `install/NOTES.md`) — лучше один проверенный вариант,
чем случайный непроверенный. Если `firefox` тоже начнёт резать — попробуй
`safari`/`ios` вручную, поменяв `fp=` прямо в ссылке.

После установки вход на сервер — только по ключу, с закреплённым хост-ключом
(команда есть в summary):

```bash
ssh -i ~/.ssh/xray-auto-install-<ip> \
    -o UserKnownHostsFile=~/.ssh/xray-auto-install-<ip>.known_hosts \
    -o StrictHostKeyChecking=yes root@<ip>
```

(`<ip>` в именах файлов — с `_` вместо точек.)

### Переменные окружения

| Переменная | Что делает |
|---|---|
| `XAI_REALITY_SNI=<домен>` | Задать Reality SNI вручную вместо случайного из пула (см. выше). |
| `XAI_TEST_BREAK_SSH=1` | Тест: сломать вход по ключу после отключения пароля (см. ниже). |
| `XAI_TEST_BREAK_FW=1` | Тест: не открыть SSH-порт в firewall (см. ниже). |

## Проверка сервера: `verify.sh`

```bash
./verify.sh <IP>            # проверки
./verify.sh --reboot <IP>   # проверки → перезагрузка → дождаться SSH → проверки
```

Запускается с той же машины, что и `install.sh`: берёт тот же ключ, закреплённый
known_hosts (`StrictHostKeyChecking=yes`) и summary. Только читает состояние
(кроме самой перезагрузки в `--reboot`). Печатает `PASS` / `FAIL` / `WARN` по
пунктам; код выхода ≠ 0, если был хоть один `FAIL`. Проверяет:

- вход по ключу снаружи; сервер не предлагает `password`/`keyboard-interactive`;
- `sshd -t` и все значения `sshd -T -C` из шага 8, наш drop-in на месте;
- nftables: ruleset загружен, `policy drop`, открыты ровно 22 и 443, сервис
  enabled; страховочных таймеров отката нет;
- `xray run -test`, `systemctl is-active xray`, порт 443 держит xray;
- Reality: SNI/target из конфига согласованы, и target повторно проверяется с
  сервера той же командой `openssl`, что при установке;
- DNS-резолв и `NTPSynchronized=yes`;
- `nf_conntrack_max = 32768`;
- своп соответствует правилу RAM (в контейнере без свопа — `WARN`; свой своп
  образа — `PASS`, скрипт его не трогает);
- права: `config.json` — `640 root:<группа xray>`, локальный summary — `600`;
- лимит journald виден в `systemd-analyze cat-config systemd/journald.conf`;
- `privateKey` и `decryption` не встречаются в `journalctl -u xray` (печатается
  только число совпадений, сами значения — никогда).

## Тестовые флаги

Нужны, чтобы одной командой проверить цепочку «сломали → таймер → доступ
вернулся → перезагрузка → доступ есть». Оба **специально ломают доступ** и
роняют установку — только для тестового сервера.

- **`XAI_TEST_BREAK_SSH=1 ./install.sh`** — после отключения пароля в наш
  drop-in добавляется `AuthorizedKeysFile` в никуда: ключ перестаёт пускать,
  установка останавливается до firewall. Через ~3 минуты таймер удаляет наш
  drop-in — возвращается вход и по паролю, и по ключу; после этого скрипт можно
  запустить заново уже без флага.
- **`XAI_TEST_BREAK_FW=1 ./install.sh`** — SSH-порт не открывается в ruleset:
  новое соединение не проходит, установка останавливается **без ссылки**. Через
  ~2 минуты таймер снимает фильтрацию (и отключает nftables) — вход по ключу
  возвращается. Сервер остаётся без firewall, а пароль уже отключён, поэтому
  повторная установка — только после переустановки ОС.

Проверено на Debian 13: оба отката срабатывают по расписанию и переживают
перезагрузку.

## Требования к локальной машине

`ssh`, `sshpass`, `ssh-keygen`. Целевой сервер — чистый **Debian 12+ или Ubuntu
22.04+** с root-доступом по паролю (как выдаёт провайдер); на более старых
скрипт отказывается сразу: строгая проверка `sshd -T` рассчитана на OpenSSH ≥ 8.7.

## Что сознательно НЕ делается

Решение основано на предметном обсуждении угроз для этого класса серверов
(одноразовый/малый VPN-сервер, а не мультиарендная инфраструктура):

- **Отдельный sudo-пользователь** — не добавляет защиты при полной
  компрометации машины: тот, кто получил доступ (украл ключ, взломал сервис),
  и так может стать root.
- **fail2ban** — на сервере нет парольной аутентификации ни для SSH (ключ
  only), ни для какого-либо другого сервиса — банить нечего.
- **Passphrase на SSH-ключе** — защищает только от кражи ключа "в холодную"
  (файл утащили, но не получили доступ к разблокированной машине). Реалистичная
  модель угроз здесь — полная компрометация локальной машины целиком, при
  которой passphrase не спасает.
- **Фиксация версии Xray-core** — ставится последний стабильный релиз на
  момент установки (версия видна в summary). Воспроизводимость хуже, зато
  исправления протокола и безопасности приходят без правки скрипта.
- **Self-steal** (свой домен и настоящий сертификат на этом же сервере в
  роли target) — закрыл бы несоответствие ASN, но требует домена и DNS;
  отложено.
- **Поиск target среди соседей по подсети/ASN** (сканирование на сайты с
  TLS 1.3 + h2 рядом с сервером) — не встроен: результат зависит от
  конкретной сети и требует ручной оценки.

Если твоя модель угроз другая (много клиентов на сервере, общий доступ к
локальной машине, требования комплаенса) — добавляй это поверх сознательно,
скрипт не мешает.

## Что делается сверх голого VLESS

- **Своп по объёму RAM** (`/swapfile`, `vm.swappiness=10`): меньше 2 GiB → 2 GiB,
  2–4 GiB → 1 GiB, больше 4 GiB → не создаётся; в LXC/OpenVZ, где `swapon`
  запрещён, установка идёт дальше без свопа. Раньше был в списке "сознательно
  не делаем" (не относится к безопасности, не хотелось усложнять установку), но
  после реального инцидента на 130.17.21.198 (2026-09-22: 967MB RAM без свопа,
  почти под завязку забиты буферами/кэшем — при всплеске нагрузки это прямой
  путь к OOM-killer'у вместо деградации) решение пересмотрено: на маленьких
  VPS своп — дешёвая подушка безопасности под такой сервис.
- **`nf_conntrack` в `/etc/modules-load.d/`** — иначе после перезагрузки
  `nf_conntrack_max = 32768` не применяется (sysctl отрабатывает раньше, чем
  загружается модуль) и лимит молча остаётся дефолтным.
- **`geoip:private` → blackhole** в маршрутизации Xray — клиенты не ходят
  через сервер в его локальную сеть и loopback. С `domainStrategy:
  IPIfNonMatch`: иначе правило по IP обходится любым доменом, который
  резолвится в приватный адрес (`localhost`, `*.nip.io`).
- **`SystemMaxUse=100M` для journald** (drop-in
  `/etc/systemd/journald.conf.d/00-xray-auto-install.conf`) — без лимита журнал
  systemd растёт неограниченно; на том же 130.17.21.198 access-лог xray (по
  одной строке на каждое новое соединение) за ~13 дней набрал 87MB и держал
  `systemd-journald` на 158MB RSS на сервере с 967MB total.
- **`"access": "none"` в log-секции `config.json`** — Xray по умолчанию пишет
  access-лог (строка `accepted tcp:...` на каждое соединение) в stdout/journald
  независимо от `loglevel`; на активном сервере это основной источник роста
  журнала из пункта выше, а сама информация (кто когда законнектился) не нужна
  для этого threat model.

## Файлы на сервере после установки

- `/usr/local/etc/xray/config.json` — конфиг Xray-core (`640 root:<группа xray>`)
- `/etc/nftables.conf` — правила фаервола
- `/etc/ssh/sshd_config.d/00-xray-auto-install.conf` — настройки SSH
- `/etc/sysctl.d/99-bbr.conf`, `/etc/modules-load.d/bbr.conf` — BBR
- `/etc/sysctl.d/99-conntrack.conf`, `/etc/modules-load.d/nf_conntrack.conf` — лимит conntrack
- `/etc/sysctl.d/99-swappiness.conf`, `/swapfile` — своп (если создавался)
- `/etc/systemd/journald.conf.d/00-xray-auto-install.conf` — лимит журнала

И на локальной машине:

- `~/.ssh/xray-auto-install-<ip>` (+ `.pub`) — SSH-ключ
- `~/.ssh/xray-auto-install-<ip>.known_hosts` — закреплённый хост-ключ сервера
- `~/xray-auto-install-<ip>-summary.txt` — сводка со ссылкой (`600`)

Страховочные `systemd-run`-таймеры (`xray-auto-install-ssh-rollback`,
`xray-auto-install-fw-rollback`) существуют только пока не подтверждены —
скрипт снимает их сам в конце успешного прогона. Если видишь их в
`systemctl list-timers` после завершения установки — что-то из проверок не
прошло, смотри вывод скрипта (`verify.sh` тоже это покажет).
